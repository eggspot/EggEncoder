## What is EggEncoder

EggEncoder is a .NET audio encoding/decoding toolkit built around a single `IMediaEncoder` abstraction (`Probe`, `ConvertFile`, `CutFile`) implemented entirely in-process by `NativeEncoder` — pure .NET + P/Invoke codec bindings, no external process, no ffmpeg dependency. Originally extracted from a music distribution platform's internal encoder project (which also had an ffmpeg-shell-out engine; that engine was dropped when EggEncoder became native-only).

## Architecture

### `IMediaEncoder` implementation

- **`NativeEncoder`** (`src/EggEncoder/NativeEncoder.cs`) — the sole `IMediaEncoder` implementation. Dispatches by file extension to the codec classes under `Codecs/`. No subprocess, no native binary dependency at all (despite the class name, which predates the managed codec rewrite — see `docs/managed-codec-rewrite-plan.md`). `Probe`/`ConvertFile`/`CutFile` (and the `Stream`-based `Probe` overloads in `NativeEncoder.Stream.cs`) each have a `CancellationToken`-accepting overload — new default-interface-method overloads on `IMediaEncoder`, not new parameters on the existing methods, so no existing compiled caller breaks. `ConvertFile`/`CutFile` check the token once per decoded block, inside the single shared `AudioCutter.DecodeSource` callback every codec's own decode loop already funnels through; `Probe`'s own check is deliberately shallow instead — once, up front, before any decode starts — since `Probe` has no equivalent single shared callback across its 20+ per-format methods. See `docs/feature-roadmap.md` item 5.

| `Wav/` | `WavReader`/`WavWriter` — RIFF/WAVE PCM I/O, the common source/sink format all codecs read from or write to. Both support 8/16/24/32-bit integer and 32-bit IEEE float (`WavWriter.Create(..., sampleFormat: WavSampleFormat.Float32)`). `WavReader` additionally decodes IMA ADPCM (`WAVE_FORMAT_IMA_ADPCM`, format tag 17, mono/stereo — `ImaAdpcmDecoder`) and MS ADPCM (`WAVE_FORMAT_ADPCM`, format tag 2, mono/stereo — `MsAdpcmDecoder`) directly into 16-bit PCM; since the file extension is still `.wav`, neither needed any changes to `NativeEncoder`/`AudioCutter` dispatch at all, just `WavReader` itself understanding each format's own `fmt` chunk extension and the `fact` chunk's authoritative total-sample count. MS ADPCM is a genuinely different algorithm from IMA ADPCM — linear prediction via a per-file coefficient table carried in the `fmt` chunk extension itself (`wNumCoef` pairs of `iCoef1`/`iCoef2`, read directly rather than hardcoded, since the format allows a non-standard table even though every real encoder emits the same standard 7-pair one), not IMA ADPCM's universal fixed step table; its block header is also grouped by field across channels (all channels' block-predictor bytes, then all deltas, then all sample1s, then all sample2s) rather than repeated per channel, and stereo interleaves one nibble per channel per byte rather than IMA ADPCM's 8-sample groups. `WavWriter` also encodes both ADPCM variants (`WavSampleFormat.ImaAdpcm`/`MsAdpcm`, mono/stereo, 16-bit input required — `ImaAdpcmEncoder`/`MsAdpcmEncoder`), block-structured and buffered internally into fixed-size blocks (a 1024-byte block align matching FFmpeg's own real encoder defaults, flushed on `Finish()` with the final short block padded) rather than written one sample at a time. IMA ADPCM's own nibble is chosen by `ImaAdpcmDecoder.QuantizeNibble`, an 8-candidate brute-force search against `ExpandNibble`'s own per-bit-term diff formula -- deliberately not FFmpeg's own `adpcm_ima_compress_sample` nibble-picking heuristic, confirmed (by computing both formulas by hand, not just reading FFmpeg's source) to optimize for a numerically different `ff_adpcm_yamaha_difflookup`-table reconstruction formula than the one FFmpeg's own decoder (and this one) actually use -- so the encoder's running predictor/step-index track in perfect lockstep with any standards-compliant decoder by construction. MS ADPCM's own nibble, by contrast, is computed via a direct closed-form formula in `MsAdpcmDecoder.CompressSample`, not a search -- confirmed FFmpeg's real `adpcm_ms_compress_sample` DOES structurally match its own decoder's reconstruction formula (just against its pre-divided-by-4 coefficient convention rather than this decoder's real, non-pre-divided one), so no search is needed; `MsAdpcmEncoder` always selects the standard table's simplest pair (predictor index 0) for every block, matching FFmpeg's own real encoder exactly (confirmed from its source: no per-block search over the other 6 standard pairs at all), and always writes the full 7-pair standard table (`MsAdpcmEncoder.Coeff1Table`/`Coeff2Table`) into the file's own `fmt` chunk extension regardless of which single pair a given block uses. Both encoders are verified bit-exact against a real, independent ffmpeg decode of files they produced, not just this project's own decoder. Both `WavReader` and `WavWriter` also support G.711 companded PCM (`WAVE_FORMAT_ALAW`/`WAVE_FORMAT_MULAW`, format tags 6/7, any channel count, full decode AND encode — `G711Codec`) directly into/out of 16-bit PCM; unlike the ADPCM variants' own block-structured encode, G.711 has no block structure or adaptive state at all, so its own encode is a simple one-sample-at-a-time companding formula and `WavSampleFormat.ALaw`/`MuLaw` select it as a `WavWriter`/`AudioCutter` destination the same way `Float32` does. A third ADPCM variant, Yamaha ADPCM (`WAVE_FORMAT_YAMAHA_ADPCM`, format tag 32, mono/stereo, full decode AND encode — `YamahaAdpcmDecoder`/`YamahaAdpcmEncoder`), is structurally simpler than IMA/MS ADPCM: confirmed directly from FFmpeg's real `adpcm.c`/`adpcmenc.c`/`adpcm_data.c` source and a real ffmpeg-produced fixture's own bytes, it has NO block structure at all -- no per-block header, no `wSamplesPerBlock` `fmt` chunk extension (`cbSize` is 0), and each channel's predictor/step state carries continuously for the entire stream, lazily initializing (predictor=0, step=127) only once, the first time a channel's `Step` is still its default 0. Nibbles are consumed in the flat interleaved sample array's own order (frame-major, channel-minor: low nibble of each byte is channel 0 / the earlier of two mono frames, high nibble is channel 1 / the later mono frame), so `WavReader`/`WavWriter` drive `ExpandNibble`/`CompressSample` directly per-sample rather than needing a `DecodeBlock`/`EncodeBlock`-style encapsulation. Like MS ADPCM's own encoder (and unlike IMA ADPCM's own 8-candidate search), `YamahaAdpcmEncoder.CompressSample` computes its nibble via a direct closed-form formula (`min(7, abs(delta) * 4 / step) + sign`) confirmed structurally identical to FFmpeg's real `adpcm_yamaha_compress_sample`, then commits it through `ExpandNibble` itself -- the same "compute directly, then commit via the shared, already-verified decode path" guarantee. Because there's no block padding, `WavWriter`'s own data chunk size is exactly `ceil(totalFrames * channels / 2)` bytes, with at most one trailing zero-pad nibble (mono, odd frame count) flushed by `Finish()`. `WavReader` also reads a `'LIST'` chunk whose own sub-type is `'INFO'` -- the standard RIFF metadata convention (title/artist/date/etc., each its own four-character-ID sub-chunk) -- exposed as `WavReader.Tags`/`ProbeResult.Tags`, keyed by the raw chunk ID, `null` if absent (most WAV files carry none). - **`Transform/`** — `BitReader`, `BitWriter`, `HuffmanTable`, `Mdct` — low-level bitstream and signal-processing primitives shared by the AAC/WMA codecs
- **`Native/` — gone.** `FlacNative.cs`/`NativeLibraryLoader.cs`/`libFLAC.dll` (the last native infrastructure in this project) were removed in `docs/managed-codec-rewrite-plan.md` item 8, the same way `WavPackNative.cs`/`wavpackdll.dll` and `Mp3Native.cs`/`libmp3lame.dll` were removed alongside their own respective managed rewrites (see the `WavPack/`/`Mp3/` rows above). There is no native binary or P/Invoke binding left anywhere in this codebase
- **`Waveform/WaveformCalculator.cs`** — streaming peak-window calculator fed blocks during decode, used by every codec's probe path to produce `ProbeResult.Waveform`; also tracks an overall peak absolute sample and running sum-of-squares across every block (independent of window finalization, so no flush step needed) to back `ProbeResult.PeakAmplitude`/`RmsLevel`. - **`Waveform/KWeightingFilter.cs`** — the two-cascaded-biquad K-weighting pre-filter ITU-R BS.1770-4 loudness measurement requires before any mean-square/gating step. Structurally similar to `Pcm.BiquadTransform` (Direct Form II Transposed, two state values per stage) but not reusable from it — the standard's own tan-prewarped bilinear-transform coefficient formula is a different parameterization from `BiquadTransform`'s RBJ-cookbook one. Coefficients verified against the reference `libebur128` source, not memory; the whole filter+gating pipeline is further confirmed against the standard's own published conformance signal (a 997Hz/-23dBFS sine must measure -23.0 LUFS) — see `docs/feature-roadmap.md` item 3
- **`Results/ProbeResult.cs`** — the public `ProbeResult` DTO returned by every `Probe` call
- **`ServiceCollectionExtensions.cs`** — `AddEggEncoder(enableLogging: true)` DI registration; registers `NativeEncoder` itself as scoped, then maps both `IMediaEncoder` and `IPcmTransformEncoder` to resolve that same scoped instance. `enableLogging: false` fully silences `NativeEncoder`'s start/completion/failure logs

### PCM transform pipeline (`src/EggEncoder/Pcm/`)

A `PcmTransformPipeline` is an ordered list of `IPcmTransform`s run on each decoded `int[]` block, between decode and the `IAudioSink` write, wired in by `AudioCutter.Pipeline.cs`. It's opt-in: the original zero-pipeline `Convert`/`Cut` overloads are untouched and remain fully streaming. `IPcmTransform.Flush()` is a default interface method (existing implementers don't need to change) for a transform that holds output back across blocks (`ResamplingTransform`, for withheld lookahead; `EchoTransform`, for a decaying repeat tail); `PcmTransformPipeline.Flush(...)` cascades it through an entire pipeline — a flushed transform's tail is pushed through every later transform's own `Apply` before that transform's own `Flush` drains it in turn — and `AudioCutter.Pipeline.cs`'s `Convert`/`Cut` call it once after the last block, before finishing the destination sink.

| Transform | Does |
|-----------|------|
| `ResamplingTransform` | Kaiser-windowed-sinc polyphase resampler (anti-aliasing on downsample, band-limited reconstruction on upsample), precomputed into a polyphase table so resampling is a table lookup plus a dot product. Holds a self-trimming window of source history across blocks and withholds a destination frame until its full tap window has genuinely arrived, rather than duplicating an edge sample at a block boundary; total output frame count is a cumulative `floor(sourceFramesSoFar * ratio)`, exact regardless of block splits. Because of that withholding, the last few frames of a stream need `Flush()` (see below) to drain — `AudioCutter`'s pipeline-aware `Convert`/`Cut` call it automatically |
| `VolumeTransform` / `PeakNormalizationTransform` | Linear gain, and two-pass peak normalization to a target dBFS (`MeasurePeak` then `Apply`, or single-pass self-measuring) |
| `LoudnessTransform` | Two-pass loudness normalization to a target LUFS (ITU-R BS.1770-4 / EBU R128 integrated loudness) -- the real perceptual-loudness counterpart to `PeakNormalizationTransform`'s own peak-dBFS target, the two serving genuinely different goals (roadmap item 3's own normalization half, unblocked once `WaveformCalculator.GetIntegratedLoudness`/`ProbeResult.IntegratedLoudness` landed). Unlike `PeakNormalizationTransform`, `Apply` has no single-pass self-measuring fallback at all -- EBU R128's own gating algorithm genuinely needs the whole signal, so a per-block "measurement" would silently normalize against the wrong number far more often than peak normalization's own same shortcut would; `MeasureLoudness` must be called first (typically with `AudioCutter.MeasureIntegratedLoudness`'s own whole-file measurement) or `Apply` throws. `null` or `double.NegativeInfinity` (EBU R128's own "measured, but below the absolute silence gate" sentinel) both pass samples through unchanged, since no finite gain reaches a finite target from either |
| `CompressorTransform` | Dynamic range compression: threshold (dBFS) / ratio / attack / release / makeup gain, the standard feedforward design. Stereo-linked envelope follower (one scalar tracking the loudest channel per frame, not independent per-channel envelopes) tracked in linear scale via a one-pole filter with separate attack/release coefficients; converted to dB once per frame for the reduction computation. Channel-count-agnostic like `FadeTransform` (no per-channel state), but fixes `sampleRate` at construction like `BiquadTransform` (the attack/release coefficients depend on it) |
| `NoiseGateTransform` | Downward expansion / noise gating: the mirror image of `CompressorTransform`, gaining reduction below threshold instead of above, via the same stereo-linked envelope follower and attack/release shape. Unlike the compressor, true digital silence (`envelopeDb == -Infinity`) is the gate's own common case rather than a boundary condition, so `ratio == 1.0` combined with silence is handled as an explicit branch rather than falling through the general `(threshold - envelopeDb) * (1 - 1/ratio)` formula -- that combination would otherwise compute `Infinity * 0`, which is `NaN` under IEEE 754, not 0 |
| `LimiterTransform` | Peak limiting: an infinite-ratio compressor (the same stereo-linked envelope follower, but the output envelope is clamped exactly AT the ceiling once it exceeds it, not merely nudged toward it by a finite ratio) plus a final per-sample hard clip to the ceiling. The hard clip is what makes this a true peak limiter rather than just "`CompressorTransform` with a very high ratio" -- a nonzero attack time lets a fast transient slip past the smoothed envelope follower before gain reduction has caught up, so the envelope-derived gain alone can't *guarantee* the ceiling; the hard clip turns that into an exact guarantee independent of attack time. `attackMs` defaults to 0 (instant), the classic brick-wall-limiter default |
| `EchoTransform` | Feedback delay / echo: a classic comb-filter delay line, one per channel. Each output sample is the dry input plus `wetGain` times the input from `delaySeconds` ago; `feedback` (must be `< 1.0`) controls how much of each repeat feeds back into the delay line to produce the next, quieter one. Fixes `channels`/`sampleRate` at construction like `BiquadTransform`/`FirFilterTransform` (the delay line is per-channel state sized up front), unlike the channel-count-agnostic compressor/gate/limiter family. The second built-in transform (after `ResamplingTransform`) to implement `Flush()` — here to drain the decaying repeat tail (a deterministic, bounded number of frames; see `EchoTransform.MaxTailSeconds`) rather than withheld lookahead. `CanChangeFrameCount` reports `true` whenever `feedback > 0`, since the tail means total output genuinely exceeds total input |
| `PanTransform` | Stereo balance/pan via independent left/right gain from a single `pan` value in [-1.0, 1.0], either `PanLaw.Linear` (balance-style: only the opposite channel attenuates, no volume dip at center) or `PanLaw.EqualPower` (constant-power: both channels attenuate by -3dB at center, `left^2 + right^2 == 1` everywhere) |
| `ChannelRemixTransform` | Mono↔stereo and general N↔M remixing (equal-weight downmix, cyclic upmix) |
| `BitDepthFormatTransform` | Rescales between the native ranges of 8/16/24/32-bit samples (this codebase has no separate "normalized" scale — every bit depth is signed and sign-extended to its own native range, e.g. 8-bit is -128..127; see `WavReader`/`WavWriter`) |
| `FadeTransform` | Fade-in/out (linear or equal-power) over a fixed total frame count, tracked across blocks the same way as `ResamplingTransform` |
| `BiquadTransform` | A single second-order IIR filter section using the RBJ Audio EQ Cookbook formulas: low/high pass, band pass, notch, all pass, peaking EQ, low/high shelf. Direct Form II Transposed (two state values per channel) |
| `ButterworthTransform` | Steeper low/high pass than a single `BiquadTransform` can provide, via `order / 2` cascaded `BiquadTransform` stages sharing a cutoff frequency, each at a different Q from the standard Butterworth pole-pair formula (maximally flat passband). `order` must be a positive even integer |
| `FirFilterTransform` | General FIR convolution (ffmpeg `afir`/general-FIR parity): applies a caller-supplied tap array identically to every channel, with no filter-design code of its own — the raw-taps constructor is the only entry point, since accepting arbitrary taps is the whole point. Keeps each channel's last `taps.Length - 1` samples as history across blocks |

`PcmTransformPipeline.ComputeOutputFormat` lets a caller learn the pipeline's final (channels, sample rate, bit depth) before the first block arrives, so the destination sink can be opened up front. Because `WavWriter` is the only sink that needs an exact frame count at open time (it writes a fixed-size RIFF header with no patch-up on `Finish()`), `AudioCutter.Pipeline.cs`'s `DeferredWavSink` buffers written blocks and only opens the real `WavWriter` in `Finish()`, once the true count (which a frame-count-changing transform like resampling can't predict up front) is known; every other destination format streams straight through since their encoder sessions don't take a frame count at all.

`Mix` (2+ same-format sources, per-input gain, silence-padded to the longest) decodes every input fully into memory — clip-length material, not multi-hour streams. `Concatenate` (2+ same-format sources) is fully streaming.

Transform instances carry cross-block state (e.g. `ResamplingTransform`'s fractional position, `FadeTransform`'s frame position, `PeakNormalizationTransform`'s measured gain, `CompressorTransform`/`NoiseGateTransform`/`LimiterTransform`'s envelope follower, `EchoTransform`'s delay line, `BiquadTransform`/`ButterworthTransform`/`FirFilterTransform`'s filter history) — build a fresh `PcmTransformPipeline` per `Convert`/`Cut`/`Mix` call rather than reusing one across multiple calls.

**Float PCM** (`Pcm/FloatSampleConverter.cs`): the pipeline itself is exclusively `int[]`-based — there's no `IPcmTransform` for float, since that would mean reworking every transform's shared contract. Instead `FloatSampleConverter.FromFloat`/`ToFloat` convert at the application boundary, using the same -1.0..1.0 ↔ 32-bit-int-native-range scale `WavReader`/`WavWriter` already use for float WAV I/O; `float.NaN` maps to 0 (silence) rather than the unspecified result of a raw `(int)double.NaN` cast, and `float.PositiveInfinity`/`NegativeInfinity` clamp to ±1.0. `AudioCutter.ReadWavAsFloat`/`WriteWavFromFloat` wrap this for the WAV case. A float WAV *source* has always decoded transparently into int PCM through `Convert`/`Cut`/`Mix`/`Concatenate` (`WavReader.IsFloatFormat` handles this on read); for a float WAV *destination*, `WavSampleFormat.Float32` (`Codecs/WavSampleFormat.cs`) can be passed to those same entry points (`Convert`/`Cut` via `CutOptions.DestinationWavFormat`/`Mix`/`Concatenate`) — it requires the destination's bit depth to already be 32 and throws `NotSupportedException` against a non-WAV destination. The default, `WavSampleFormat.Integer`, is unchanged from before this option existed.

### Media packet model (`src/EggEncoder/Media/`)

The packet-level model shared by every live source and output in `docs/live-ingest-restream-plan.md`
(item 1), so video is remuxed without decoding. `MediaKind`/`MediaCodec`, `MediaTrackInfo` (a
validating record: timescale > 0, ids/sizes non-negative; codec configuration is track-level and a
mid-stream change bumps `ConfigVersion`), `MediaTrackSet` (unique track ids), `MediaPacket` (`readonly
record struct`, `long` PTS/DTS ticks in the track's own timescale, length-prefixed AVCC/HVCC payloads
for H.264/H.265, raw AAC access units with no ADTS) and `IMediaPacketSink` (the async output
contract; no implementation yet). `MediaTimestamp.Rescale` is the only timescale conversion
(`Int128` intermediate, round half to even, `OverflowException` instead of wrapping).
`AnnexBConverter` converts one access unit AVCC ↔ Annex B. `AvcDecoderConfigurationRecord`/
`HevcDecoderConfigurationRecord` parse and build avcC/hvcC byte-exactly via the internal, bounds-checked
`ConfigurationRecordReader`/`ConfigurationRecordWriter`. `H264SpsParser`/`H265SpsParser` read SPS
header fields only (profile/level/chroma/bit depth/cropped size, plus the RFC 6381 `CODECS` string via
`H264SpsInfo.CodecsString`/`HevcProfileTierLevel.ToCodecsString`) through the internal `RbspReader`
(emulation-prevention removal + Exp-Golomb on top of `Transform.BitReader`, every overrun an
`InvalidDataException`). `MediaPacketFactory.FromEncodedAudioFrame` adapts `IStreamingEncoder` output.
Tests use `Codecs/Mov/test.mp4` (real H.264 access units via `MovVideoDemuxer`) plus real
ffmpeg/x264/x265-produced avcC/hvcC records baked in as hex (`Media/MediaFixtures.cs`) and a synthetic
`TestUtilities/RbspBuilder` for SPS branches no fixture reaches.

### FLV container (`src/EggEncoder/Containers/Flv/`) and AMF0 (`src/EggEncoder/Live/Rtmp/Amf0/`)

`docs/live-ingest-restream-plan.md` item 2. `FlvTagBodyParser` classifies one audio/video tag body
(shared with the coming RTMP server, whose message bodies have the same layout) into a `FlvTagBody`
ref struct: legacy AVC/AAC/MP3 (plus the non-standard HEVC CodecID 12 on read) and Enhanced-FLV
`avc1`/`hvc1`/`av01`/`vp09`; unknown codecs and Multitrack/ModEx are a typed `Unsupported` result,
never an exception, while a body too short for its own header is `InvalidDataException`.
`FlvDemuxer` is incremental (`Feed`/`Complete`, callbacks for track sets and packets; video track
0, audio track 1, timescale 1000), validates avcC/hvcC through `Media/`'s records, reads SPS
dimensions (unreadable SPS leaves them 0, not fatal), unwraps 32-bit timestamps, bumps
`ConfigVersion` on a differing sequence header, holds at most 1,024 packets until every
header-declared track is configured, and is strict about the container (signature, DataOffset,
`PreviousTagSize`, truncation) but skips-and-counts unusable tags. `FlvFileSource` is the async
`IAsyncEnumerable<MediaPacket>` wrapper over any `Stream`. `FlvWriter` implements `IMediaPacketSink`
over a synchronous core, forward-only (no `CanSeek`; `onMetaData` duration stays 0), legacy tags for
H.264/AAC/MP3 and Enhanced FourCC tags for HEVC/AV1/VP9, CodedFramesX for HEVC frames with no
composition offset as ffmpeg does. `FlvMetadata` wraps `onMetaData`. The AMF0 codec
(`Amf0Reader`/`Amf0Writer`/`Amf0Value`) lives where RTMP item 3 will reuse it; the reader's bounds
(depth 32, strings 64 KiB, 1,024 properties, counts checked against bytes left) are fixed constants
for now. Fixtures: ffmpeg 9-produced `h264_aac.flv` (x264 with B-frames + AAC), `hevc.flv`
(Enhanced FLV) and `mp3.flv`, with ffprobe ground truth in `FlvDemuxerTest`; an
`EGGENCODER_FFMPEG_ORACLE=1`-gated test runs the real `ffprobe` on `FlvWriter` output.

### RTMP protocol core (`src/EggEncoder/Live/Rtmp/`)

`docs/live-ingest-restream-plan.md` item 3: pure, synchronous, socket-free building blocks the
coming `RtmpServer` (item 4) and RTMP client (item 6) share. `RtmpHandshake` is the simple
version-3 handshake as a byte-level state machine for either side (`Start`, then
`Process(BytesExpected bytes)` until `IsComplete`; RTMPE and other versions throw; the C2/S2 echo
is not compared byte for byte, since digest-handshake publishers don't echo exactly).
`RtmpChunkReader` reassembles `RtmpMessage`s (`Type`, `StreamId`, 32-bit wrapping `Timestamp`,
owned `Payload`) from an incremental `Feed`: header types 0-3 (a type 3 that starts a message
repeats the previous delta; right after a type 0 that delta is the type 0 timestamp, the spec's own
reading, decided by research in PR #140), chunk stream ids 2-65599, extended timestamps
(continuations repeat them per the spec; a peer that omits the repeat, as older librtmp/ffmpeg did,
is detected on the first continuation by comparing the next four bytes with the extended value,
and that decision is latched per chunk stream), interleaving across chunk streams; it applies Set Chunk Size,
Abort and Window Acknowledgement Size itself (`TryTakeAcknowledgement` says when to ack) and still
reports them; `Complete()` (the connection closed) turns a chunk or message cut short into an
`RtmpProtocolException`, since `Feed` alone can't tell truncation from a slow peer. `RtmpChunkReaderOptions` holds the security-posture bounds (chunk size, message
length, chunk stream count, buffered bytes; defaults and hard ceilings), checked before anything
is allocated; buffers grow only as payload arrives. Every violation throws `RtmpProtocolException`
(an `IOException`; `InvalidDataException` is sealed) and faults the reader. `RtmpChunkWriter`
chooses the most compact header per chunk stream (type 0 when the timestamp goes backwards; never
a type 3 directly after a type 0, which peers read differently).
`RtmpProtocolControl`/`RtmpUserControl` build and read control messages and events;
`RtmpCommand` (AMF0 command, type 20; AMF0 errors wrapped) and `RtmpDataMessage` (type 18;
`@setDataFrame`/`onMetaData` to `FlvMetadata`) build and read the NetConnection/NetStream flow.
The AMF0 bounds stay `Amf0Reader` constants (they equal the plan's defaults). Fixture:
`ffmpeg_publish.bin`, every byte ffmpeg 9.0.2 sent publishing `h264_aac.flv` to the test-only
`RtmpTestReceiver` (its connect spans a type 3 continuation at the default 128-byte chunk size);
`RtmpFfmpegOracleTest` re-runs the live publish when `EGGENCODER_FFMPEG_ORACLE=1`, and writes a new
capture when `EGGENCODER_RTMP_CAPTURE_PATH` is also set.

### Streaming (`src/EggEncoder/Streaming/`)

A push-style, incremental live-streaming/HLS packaging effort layered on top of the codec/container
infrastructure above -- genuinely independent of the `IMediaEncoder` file/`Stream` surface and of
every per-codec `XxxEncoder`/`XxxEncoderSession` whole-file type (no destination file/`Stream` or
known total length required anywhere in this surface). See `docs/streaming-plan.md` for the full
ordered plan, acceptance criteria per item, and what's merged versus still open.

**Planned, not yet implemented**: the rest of live ingest and restream (the packet model, FLV
demux/mux and the RTMP protocol core above are done; still open: RTMP server/client incl. RTMPS, video tracks in the
fMP4/MPEG-TS muxers, file/URL/HLS live sources with `-re` pacing, restream fan-out, later SRT) -- see
`docs/live-ingest-restream-plan.md`, which also records the decided async API shape for network I/O
(an explicit exception to this surface's synchronous-callback idiom) and the listener security
defaults every network-facing item must meet.

- `IStreamingEncoder`/`EncodedAudioFrame`/`EncodedAudioFrameCallback` (`Streaming/IStreamingEncoder.cs`,
  `Streaming/EncodedAudioFrame.cs`) — `Write(ReadOnlySpan<int>)` buffers PCM and invokes the callback
  once per encoded frame as soon as a full codec-native frame's worth of samples has arrived;
  `Complete()` flushes any partial trailing frame. `Streaming.Aac.AacStreamingEncoder` (`Streaming/Aac/
  AacStreamingEncoder.cs`) is the only implementation so far -- mono AAC-LC, the same scope as
  `Codecs.Aac.AacEncoderSession`, reusing that same codec's `AacFrameEncoder` MDCT/quantization logic
  unchanged (see the `Aac/` row above for how that refactor is shared between both callers).
  `EncoderDelaySamples` (`1024`) documents this encoder's own one-frame MDCT lookahead.
- `Streaming.Mp4.FmpInitSegmentWriter`/`FmpMediaSegmentWriter` (`Streaming/Mp4/`) — build a
  fragmented MP4 (fMP4/CMAF) init segment (`ftyp`+`moov`, once per rendition, no samples of its own)
  and media segments (`moof`+`mdat`, one call per segment) for a single mono AAC-LC track.
  `FmpMediaSegmentWriter` is stateful across calls (`sequence_number`/`baseMediaDecodeTime` both
  carry forward, which is what makes segment N+1 play seamlessly after segment N) -- build a fresh
  instance per rendition. `Mp4EncodedFrame` is the durable `(byte[] Payload, int SampleCount)` shape
  a caller collects `EncodedAudioFrame`'s own `ref struct` payload into before handing a batch to
  `BuildMediaSegment` (a `ref struct` can't itself live in a list spanning more than one callback
  call). Backed by two new shared primitives placed alongside `MovAtomReader` in `Codecs.Mov` rather
  than in `Streaming` itself, since both are low-level ISOBMFF plumbing, not streaming-specific:
  `Mp4BoxBuilder` (a minimal big-endian box-content builder, the write-side counterpart to
  `MovAtomReader`'s own read-side box-tree walk) and `Mp4EsdsParser.BuildAudioSpecificConfig`/
  `BuildEsdsBoxContent` (the write-side counterpart to that type's existing `esds`-parsing methods).
  `ftyp` brand values and every box's own field layout/ordering were confirmed against a real
  ffmpeg-produced CMAF fMP4 fixture's own bytes, not assumed from the ISO/IEC 14496-12/23000-19 spec
  text alone. Primary conformance oracle: self-parse the init segment via `MovAtomReader` directly
  (works unchanged, zero new production reader code) and media segments via a small, test-only
  moof/traf/tfhd/tfdt/trun reader (deliberately not folded into `Mp4SampleTable`, which only
  understands the non-fragmented stsz/stco/stsc layout -- a genuinely different box set). A full
  `ffmpeg`-decode attempt against this writer's own output surfaced a **pre-existing**, unrelated
  gap in `AacFrameEncoder`'s own bitstream (reproducible identically from its existing ADTS file
  output) -- `ffprobe`'s own container-metadata reporting (this item's actual acceptance bar) is
  unaffected and passes; see `docs/streaming-plan.md` item 2's own status note for the full detail.
- `Streaming.IStreamingSink` (`Streaming/IStreamingSink.cs`) -- an I/O-agnostic HLS output
  destination (init segment, media segments, a playlist rewritten on every change, and segment
  deletion for a future live sliding window). Three implementations, all in `Streaming/`:
  `FileSystemStreamingSink` (a directory on disk, `init.mp4`/`segment_{n}.m4s`/`playlist.m3u8`, an
  optional file-name prefix for multi-rendition use), `InMemoryStreamingSink` (no filesystem at all
  -- the primary vehicle for this surface's own tests), and `DelegateStreamingSink` (four
  constructor-supplied delegates, one per interface member -- the concrete answer to "a user
  callback for HTTP/S3 upload" without writing a full class).
- `Streaming.Hls.HlsSegmenter`/`M3u8PlaylistWriter`/`HlsSegmentDescriptor` (`Streaming/Hls/`).
  `HlsSegmenter.AddFrame` takes an `EncodedAudioFrame` directly (copying `Payload` into
  its own accumulating list internally), so a caller wires `AacStreamingEncoder.Create(..., frame =>
  segmenter.AddFrame(frame))` with no manual conversion step; it writes the init segment immediately
  at construction, accumulates frames until their cumulative duration reaches a configured
  `targetDurationSeconds` *or more* (segments are cut on frame boundaries only, so a real segment's
  duration is always >= target by at most one frame), cuts a segment via item 2's
  `FmpMediaSegmentWriter`, and rewrites the playlist after every cut. Two modes, chosen by which
  constructor is used (both delegate to one shared private constructor so they can't drift apart):
  a VOD constructor (every segment ever produced stays in the playlist) and a live constructor
  taking `liveWindowSize` (throws `ArgumentOutOfRangeException` if less than 1) -- once more
  segments have been produced than that window retains, `CutSegment` drops the oldest in a `while`
  loop, advancing `EXT-X-MEDIA-SEQUENCE` and calling `IStreamingSink.DeleteMediaSegment` for each;
  no `EXT-X-ENDLIST` is written in live mode until `Complete()` is actually called. `M3u8PlaylistWriter`'s
  own `EXT-X-TARGETDURATION` value is **not** simply the configured target echoed back -- `HlsSegmenter`
  tracks the real maximum segment duration observed so far and writes `ceil(max(configured,
  observed))` on every rewrite, so the tag can never be violated by a segment the playlist already
  lists (RFC 8216 §4.3.3.1). A `SegmentFormat` constructor parameter (`Fmp4`, the default, or
  `MpegTs`) picks which container `CutSegment` builds -- `MpegTs` skips writing an init segment at
  all, omits `EXT-X-MAP` from the playlist, and uses a `.ts` segment URI extension instead of
  `.m4s`, since MPEG-TS carries its own PAT/PMT inside every segment.
- `Streaming.MpegTs.MpegTsMuxer`/`MpegTsCrc32` (`Streaming/MpegTs/`) -- the alternative,
  ADTS-framed segment format to `FmpMediaSegmentWriter`'s own fMP4/CMAF one. Every call to
  `BuildSegment` produces one complete, independently-parseable `.ts` file: PAT + PMT (declaring
  one `stream_type=0x0F`/ADTS-AAC stream) repeated at the start, then one PES packet per frame,
  split across 188-byte TS packets (`adaptation_field_control`=01/payload-only always, even for a
  short final packet -- plain `0xFF` stuffing, never an adaptation field, confirmed against a real
  ffmpeg-produced `.ts` fixture). Each PES's own PTS (the MPEG-TS-mandated 90kHz clock, a different
  timescale from fMP4's own configurable one) is `round(cumulativeSamplesBeforeThisFrame * 90000.0
  / sampleRate)`, computed from the running TOTAL sample count rather than accumulated as a fixed
  per-frame delta -- `1024 * 90000 / 44100` isn't an integer, so a naive delta would drift
  unboundedly over a long stream, while this bounds the error to at most ±0.5 ticks at any point.
  Every segment is an independently-parseable file with its own fresh PAT/PMT/continuity counters
  (matching real HLS TS segmenters' own convention), but PTS continuity across segments is still
  preserved via the muxer's own internal running sample count -- build a fresh instance per
  rendition, the same "stateful, one per rendition" shape `FmpMediaSegmentWriter` already
  established. `MpegTsCrc32` is ISO/IEC 13818-1 Annex B's own PSI-table CRC-32: same polynomial and
  bit direction as `Codecs.Opus.OggCrc32`, but a different initial value (0xFFFFFFFF vs. 0) -- not
  interchangeable despite the shared shape, so it's its own small implementation. PCR is not
  implemented (a deliberate, documented MVP scope limitation -- see docs/streaming-plan.md item 4's
  own status note for what this could affect and why it wasn't pursued further).
- `Streaming.Hls.M3u8MasterPlaylistWriter`/`HlsRenditionDescriptor` (`Streaming/Hls/`) -- a
  top-level playlist listing multiple audio-bitrate renditions, each a complete, independent
  audio rendition (not an `EXT-X-MEDIA:TYPE=AUDIO` alternate-track-alongside-video grouping, a
  deliberately deferred option -- the simpler structure real-world podcast/radio HLS output
  commonly uses). Reuses `M3u8PlaylistWriter.Version` directly rather than a separate constant, so
  the two writers can never disagree about which `EXT-X-VERSION` to declare. `CODECS="mp4a.40.2"`
  for AAC-LC and the overall `#EXT-X-STREAM-INF:BANDWIDTH={n},CODECS="{s}"` + URI shape were
  confirmed against a real multi-variant HLS master playlist (ffmpeg's own `-var_stream_map`
  output).
- `Streaming.LiveAudioPump`/`DriftPolicy` (`Streaming/`) -- feeds PCM from a genuinely live source
  (a microphone callback, an incoming network stream) into an `IStreamingEncoder` on the source's
  own schedule. `PushSamples(ReadOnlySpan<int> interleavedSamples, DateTimeOffset?
  captureTimestamp = null)`: under `DriftPolicy.SilenceFill`, once actual-so-far falls more than a
  configurable threshold behind wall-clock-implied-so-far (computed from the first captured
  timestamp), it inserts exactly enough zero-valued samples to close the gap before the next real
  samples go through; under the default `DriftPolicy.Ignore`, or whenever `captureTimestamp` is
  omitted on a given call (regardless of policy), that call is pure pass-through -- drift detection
  needs a real clock to compare against, and silently inventing one would be worse than not
  detecting drift at all. Reads `Channels`/`SampleRate` directly from the wrapped encoder, so the
  pump can never disagree with it about either value.
- `Streaming.Opus.OpusStreamingEncoder` (`Streaming/Opus/`) -- the second `IStreamingEncoder`
  implementation (item 8's own Opus sub-item), same scope as
  `Codecs.Opus.OpusEncoderSession` (fixed 48kHz, mono/stereo, 16-bit PCM), reusing that session's
  own Concentus-backed encode internals unchanged. Unlike `AacStreamingEncoder`,
  `EncoderDelaySamples` is a per-instance property reading the underlying encoder's own
  `Lookahead` directly, not a project-wide constant -- Opus's lookahead isn't architecturally fixed
  at one value the way AAC-LC's one-MDCT-frame delay is. Also unlike `AacStreamingEncoder`, every
  emitted frame's own `SampleCount` is always the full `960` -- Opus has no bitstream-level
  short-final-frame concept, so a partial tail's real-vs-padding distinction only matters at the
  container level, out of scope for this raw packet-level encoder. `Complete()` drains the
  encoder's own lookahead through the normal buffering path, but (unlike
  `OpusEncoderSession.Finish()`) does **not** unconditionally emit a final all-zero frame when
  nothing remains pending afterward -- that exists in the file-based session purely to flag an Ogg
  page's own end-of-stream bit, a container-level concept this raw-packet encoder has none of.
- `Streaming.Mp3.Mp3StreamingEncoder` (`Streaming/Mp3/`) -- the third `IStreamingEncoder`
  implementation (item 8's own MP3 sub-item), same scope as
  `Codecs.Mp3.Mp3EncoderSession` (mono/stereo, 32000/44100/48000Hz, CBR only), reusing
  `Mp3FrameEncoder`'s own encode internals unchanged. Writes no dedicated "Info tag" (LAME-tag)
  header frame and no ID3v2 tag -- both are container/file-level conventions with no equivalent
  for a raw, open-ended frame stream; `Mp3Encoder.EncoderDelaySamples` (the existing, already
  empirically-measured `1680`) remains the right value for a muxer here to use directly. Unlike
  `OpusStreamingEncoder`, this encoder reports each frame's own *real* sample count rather than
  always the nominal `1152` -- tracking it costs nothing extra here, the same way it doesn't for
  `AacStreamingEncoder`, since `Mp3EncoderSession.Finish`'s own existing design already computes
  the real remaining count before padding it. `Complete()`'s own mandatory flush frame (draining
  the one-granule MDCT history -- the same real, previously-found-and-fixed requirement
  `Mp3EncoderSession.Finish` itself documents) is purely synthetic and reports a real sample count
  of `0`. Since MP3 frames are self-delimiting with no container needed at all, the streaming
  encoder's own raw frames are simply concatenated directly into a file for conformance testing,
  decoded through the project's own public `Mp3Decoder` (NLayer).
- `Streaming.Flac.FlacStreamingEncoder` (`Streaming/Flac/`) -- the fourth and last
  `IStreamingEncoder` implementation (item 8's own FLAC sub-item, completing it), same scope as
  `Codecs.Flac.FlacEncoderSession` (any channel count, 1-32 bits per sample), reusing
  `FlacFrameEncoder`'s own encode internals unchanged. Genuinely simpler than the other three, for
  two real codec-level reasons: this encoder's own FIXED predictors are purely causal (never look
  at "future" samples), so there is no lookahead to drain at all (`EncoderDelaySamples` is always
  `0`); and FLAC's own frame format natively allows a final block shorter than the nominal size
  with no padding, unlike AAC-LC/Opus/MP3's own fixed-or-padded sizes -- `Complete()` just flushes
  whatever's pending, no mandatory extra frame. **Genuinely not independently decodable**, unlike
  the other three: `FlacFrameEncoder`'s own existing frame header always defers sample-rate and
  bits-per-sample to STREAMINFO (a pre-existing characteristic of this project's frame encoder, not
  introduced here) -- building a STREAMINFO (a whole-stream, container-level concept) is out of
  scope for this raw packet-level encoder, the same boundary every other `IStreamingEncoder` already
  draws. `FlacEncoderSession.WriteStreamInfoPayload` was widened from `private` to `internal` (zero
  behavior change) so this item's own conformance tests can build a real STREAMINFO out-of-band and
  reuse that exact bit layout rather than duplicating it. Conformance: unlike the lossy AAC/Opus/MP3
  sub-items' own SNR-floor checks, this verifies EXACT sample equality after a full decode (via the
  project's own `FlacDecoder`) -- the same bar `docs/managed-codec-rewrite-plan.md` already holds
  every lossless codec in this project to.

### Native binary packaging

**There is none.** `docs/managed-codec-rewrite-plan.md` item 8 removed the last native binary
(`libFLAC.dll`) and its supporting infrastructure (`NativeLibraryLoader.cs`, `FlacNative.cs`,
the corresponding `EggEncoder.csproj` `<None>` packaging entries and `THIRD-PARTY-NOTICES.md`

and tests on `windows-latest`/`ubuntu-latest`/`macos-latest` to prove it.

### External NuGet dependencies (product code)

Zero native dependency isn't the same as zero *external* dependency: `Concentus` (Opus),

### Native AOT

`EggEncoder.csproj` sets `IsAotCompatible=true` (enables the trim/AOT/single-file Roslyn analyzers on every build). The codebase relies only on AOT-safe constructs now that no P/Invoke remains at all — no `[LibraryImport]`/`[DllImport]`, no `[UnmanagedCallersOnly]` native callbacks (`FlacDecoder`'s own decode callback was this pattern's last example, until it was replaced by the pure managed decoder in `FlacFrameDecoder`; `WavPackEncoderSession`'s own encode callback was replaced by the pure managed `WavPackBlockWriter`/`WavPackEntropyEncoder` before that). `src/EggEncoder.AotSmokeTest/` is a `PublishAot=true` console project, multi-RID (`win-x64`/`linux-x64`/`osx-arm64`), that round-trips WAV → MP3/FLAC/WavPack → probe through a real native-compiled binary on every OS in CI — see "Testing Conventions" below. If you add a dependency or interop call, make sure it doesn't reintroduce reflection-based marshaling, `Reflection.Emit`, or a native binary dependency.

## Testing Conventions

- Framework: **xUnit** + **FluentAssertions**
- Pattern: **AAA** (Arrange / Act / Assert)
- Naming: `Feature_Condition_ExpectedBehavior` (e.g., `Probe_WavFile_Should_Return_Correct_Metadata_And_Waveform`)
- Tests live in `src/EggEncoder.UnitTests/`, mirroring the `src/EggEncoder/` folder structure
- Fixture audio files (`.wav`/`.flac`/`.mp3`/`.aac`/`.wma`/`.wv`/`.mov`/`.mp4`, plus raw `.pcm` ground-truth references for cross-check tests) live alongside their tests and are copied to the test output directory — see `<None ... CopyToOutputDirectory>` entries in `EggEncoder.UnitTests.csproj`
- Round-trip and cross-check tests (e.g. `FlacFfmpegCrossCheckTest`) validate native codec output against ffmpeg-produced reference fixtures checked into the repo — no external ffmpeg install is needed to run the tests, only the fixture files themselves
- `src/EggEncoder.AotSmokeTest/` covers Native AOT: it's a separate `PublishAot=true` console project (not an xUnit test, since xUnit runs under the JIT) that CI publishes with `dotnet publish -r <rid>` (the RID matching whichever OS the current CI matrix leg is running on — `win-x64`/`linux-x64`/`osx-arm64`) and then executes, to catch AOT/trimming regressions that the build-time analyzer alone can't (e.g. inside the `NLayer` dependency, which ships no AOT metadata of its own)

## Benchmarks

`src/EggEncoder.Benchmarks/` is a standalone [BenchmarkDotNet](https://benchmarkdotnet.org/) console project — local, manual, point-in-time performance measurements, not part of the test suite and not run in CI. Covers WAV I/O throughput (`WavIoBenchmarks`), end-to-end decode+encode throughput for WAV→MP3/FLAC (`AudioCutterBenchmarks`), `AacEncoderSession`'s own incremental streaming push throughput (`AacStreamingBenchmarks`), and pure decode throughput for FLAC/MP3/WavPack/TTA (`CodecDecodeBenchmarks`) — see [docs/benchmarks.md](docs/benchmarks.md) for how to run it and what's not yet covered.

## Release Process

Fully automatic tag-based versioning — every push to `main` triggers a release:

1. Push / merge to `main`
2. CI analyzes commit messages since last tag using conventional commits:
   - `fix:` / `perf:` / `chore:` → **patch** bump (1.1.0 → 1.1.1)
   - `feat:` → **minor** bump (1.1.0 → 1.2.0)
   - `BREAKING CHANGE` / `feat!:` → **major** bump (1.1.0 → 2.0.0)
3. Version derived from last git tag (not csproj) → builds with `-p:Version=` → tests → packs → publishes to NuGet
4. Creates git tag `v<version>` + GitHub Release with artifacts
5. Concurrency group serializes publish runs to prevent tag race conditions

No manual version editing needed. No commits pushed back to main. Just use conventional commit prefixes.

## Working Style

- **NEVER push directly to `main`** — always create a feature branch and open a PR
- Break complex tasks into smaller incremental commits
- A single PR should focus on one logical change
- Commit and push to the feature branch after each verified, self-contained unit of work
- Use conventional commit prefixes (`feat:`, `fix:`, `perf:`, `chore:`, `docs:`) — the publish pipeline auto-detects version bumps from these
- Any change to the bundled native binaries or their packaging must be reflected in `THIRD-PARTY-NOTICES.md`
